# EchoLearn — Deployment Guide

## 1. Database — Supabase or Neon (free Postgres)

**Supabase**
1. Create a project at https://supabase.com.
2. Go to Project Settings → Database → Connection string (URI, "Session" mode).
3. Copy it into `DATABASE_URL` (backend env).

**Neon**
1. Create a project at https://neon.tech.
2. Copy the connection string from the dashboard into `DATABASE_URL`.

Then run the migration once against the new database:

```bash
cd backend
pip install -r requirements.txt
alembic upgrade head
```

## 2. Vector store

Local Chroma (`app/rag/vectorstore.py`) persists to disk at `CHROMA_PATH`. On a free-tier
host without a persistent volume, that data is wiped on every redeploy/restart — fine
for a demo, not for production.

**To use a persistent volume (Render):** `render.yaml` already mounts a 1GB disk at
`/data`, with `CHROMA_PATH=/data/chroma`.

**To switch to Qdrant Cloud instead:**
1. Create a free cluster at https://cloud.qdrant.io.
2. Add `qdrant-client` to `requirements.txt`.
3. Set `QDRANT_URL` and `QDRANT_API_KEY` env vars.
4. Swap the vectorstore import from `app.rag.vectorstore` to
   `app.rag.vectorstore_qdrant` in `background.py`, `documents/routes.py`, and
   `rag/langgraph_pipeline.py` (the module exposes the same `add_chunks` / `search` /
   `delete_document` functions, drop-in compatible).

## 3. Backend — Render or Railway

**Render**
1. Push this repo to GitHub.
2. New → Blueprint → point at the repo (uses `backend/render.yaml`).
3. Fill in the env vars marked `sync: false` in the Render dashboard:
   `DATABASE_URL`, `GROQ_API_KEY`, `GEMINI_API_KEY`, `RESEND_API_KEY`, `FRONTEND_URL`.
4. Deploy. `JWT_SECRET` is auto-generated by the blueprint.

**Railway**
1. New Project → Deploy from GitHub repo, root directory `backend/`.
2. Railway auto-detects `railway.json` and builds the Dockerfile.
3. Add the same env vars as above in the Railway dashboard, plus `STORAGE_PATH` and
   `CHROMA_PATH` if you're not using the Docker defaults.
4. Attach a persistent volume if you want Chroma data to survive redeploys.

## 4. Frontend — Vercel

1. Import the repo into Vercel, set the root directory to `frontend/`.
2. Vercel auto-detects Next.js (`vercel.json` is present but minimal — no overrides needed).
3. Set the environment variable `NEXT_PUBLIC_API_URL` to your deployed backend URL
   (e.g. `https://echolearn-backend.onrender.com`).
4. Deploy.

## 5. Post-deploy checklist

- [ ] Update `FRONTEND_URL` on the backend to your real Vercel URL (used for CORS and
      email links) — redeploy the backend after changing it.
- [ ] Update `NEXT_PUBLIC_API_URL` on the frontend to your real backend URL, redeploy.
- [ ] Verify Resend is out of sandbox mode (or that you've verified a sending domain)
      so verification/reset emails reach real users, not just your own inbox.
- [ ] Confirm `alembic upgrade head` ran successfully against the production database
      (check the Dockerfile's startup command logs).
- [ ] Rotate `JWT_SECRET`, `GROQ_API_KEY`, `GEMINI_API_KEY`, `RESEND_API_KEY` if they
      were ever committed or shared — set them only via each host's env var UI, never
      in a committed `.env` file.

## 6. Rotating env vars later

- **Render**: Dashboard → service → Environment → edit value → triggers automatic redeploy.
- **Railway**: Project → service → Variables tab → edit → redeploy.
- **Vercel**: Project → Settings → Environment Variables → edit → redeploy (or it
  applies on next deploy).

Never commit `.env` — only `.env.example` (placeholders) is tracked in git.
